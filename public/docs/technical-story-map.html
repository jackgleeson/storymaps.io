Technical story map

1 min read

On this page
How it's laid out When to use it

The user doesn't have to be a person. In a technical story map the users are systems, such as a mobile app, a payment provider or a screen in the shop, and the steps are the calls they make. Engineering gets the same view of the work that product gets from a classic story map.

Try it now

Open the order API behind a coffee app, with each step an API call.

Open practice story map

How it's laid out

  • Users are the systems that call yours, such as Mobile app and Payment provider.
  • Activities are what each system is trying to do, such as Place an order.
  • Steps are the calls, in the order one request makes them: GET /menu, POST /orders, then the webhook back.
  • Tasks are the engineering work behind each call. Mark edge cases as Rose cards, the legend's colour for them, such as a webhook that arrives twice.

Slice it the same way as any story map. The first slice gets one request working end to end. Later slices harden it: retries, rate limits, monitoring.

Tip. Tag tasks by service or team, such as backend and payments. Search and filter a story map then shows one team its work across every slice.

When to use it

  • Designing an API, an integration or a data pipeline.
  • Planning a migration, with the old and new systems as users.
  • Showing product what the engineering work behind a feature really is.

A technical story map works well next to the future story map of the same product. Start a story map project keeps them together as tabs.
